# Muses Web: a lightweight browser client (self-hosted by the desktop app)

Read only: this file and the last 3 sections of `HANDOFF.md`. **Use the zip the owner attached.** Four accounts, one after the other: WEB1, WEB2, WEB3, WEB4. Each returns the full updated `Muses.zip`.

## Goal and honest architecture
The owner finds the desktop app heavy and battery hungry (Compose/Skia rendering, animated backdrops, a large JVM heap). He wants a **browser version**: simple themes, simple glass, no animated orbs, a click-to-speak voice button instead of a hotkey, and the same music.
**Fact about the code:** all the logic that finds music, resolves YouTube Music streams (cipher tiers, PoToken, NewPipe fallback), manages the account and fetches lyrics is **JVM-only** (`shared/src/jvmSharedMain`: `Innertube.kt`, `InnertubeParser.kt`, `PlayerClient.kt`, `StreamResolver.kt`, `YouTubeLyrics.kt`, Ktor/OkHttp, NewPipeExtractor). There is no JS/Wasm target and a browser cannot call YouTube directly (CORS, signed and IP-bound stream URLs, PoToken). So the browser client needs a backend that reuses this code.
**Decision:** the existing desktop app gets a **web server mode** (embedded, headless-capable). The browser UI is a small static web app served by it. The heavy part (Compose UI, animations, backdrops) is simply not running in this mode.
- Server: the JDK's built-in `com.sun.net.httpserver.HttpServer` (add the JDK module `jdk.httpserver` to the packaged runtime `modules(...)` list in `desktopApp/build.gradle.kts`, the same way `jdk.management` was added; **this is a JDK module, not a Gradle dependency; add NO Gradle dependencies**). JSON with the existing kotlinx.serialization. Live events with Server-Sent Events. No WebSocket needed.
- Playback in the browser: the server resolves the stream URL and **proxies the bytes with HTTP Range support** (`/api/stream/<videoId>`), so the browser `<audio>` element decodes with hardware acceleration (low CPU and battery) and the JVM only forwards bytes. The desktop audio engine (EQ, spatial, crossfade) is not used in this mode; say so in the UI.
- Account: the web UI uses the account already signed in inside the desktop app (cookies stay in the JVM); the browser never sees them.
- Voice: the web UI records short audio with a **click-to-speak button** and POSTs it to the server, which reuses the existing offline recognizer and command parser (`DesktopVoice*`). Nothing is stored (same rules as the desktop voice feature).
- Honest limits: the desktop app must be running (headless/tray) for the web client to work; it is NOT a public website (YouTube blocks datacenter IPs and the ToS forbids re-hosting), it is a personal server for you and your devices; on a LAN device the microphone needs HTTPS (browsers only allow it on localhost or HTTPS), so voice works on the same PC and over LAN only with HTTPS (not in v1).

## API contract (all JSON, same origin, `Authorization`-free because of the session cookie; `GET` unless noted)
`/api/ping` -> `{version, signedIn}`; `/api/home` -> shelves `[{title, kind, items:[Item]}]`; `/api/search?q=` -> sections of `Item`; `/api/suggest?q=` -> `[string]`; `/api/library` -> playlists the account owns and saved ones;
`/api/playlist/{id}` -> `{title, owner, editable, items:[Track]}`; `/api/track/{videoId}` -> `{title, artists, album, durationMs, art:{small,large}, palette:[3 hex colours], liked}`; `/api/stream/{videoId}` -> audio bytes with `Range` support, `Content-Type`, `Accept-Ranges`;
`/api/lyrics/{videoId}` -> `{synced:[{ms,text}]|null, plain:string|null}`; `POST /api/like/{videoId}` `{liked}`; `POST /api/playlist/{id}/add` `{videoId}`; `/api/art?u=` -> proxied, size-capped image (allowlisted hosts only);
`/api/events` (SSE) -> `{type:"signedIn"|"libraryChanged"|"voice", ...}`; `POST /api/voice` (audio body, 16 kHz mono WAV or webm/opus, max 15 s) -> `{heard?:string, action, result, candidates?:[Item]}` (the recognised text is returned to the page once and never stored).
`Item = {id, type:"song"|"album"|"playlist"|"artist", title, subtitle, art, videoId?, browseId?}`; `Track = {videoId, title, artists, durationMs, art}`. Keep field names exactly; add fields only if needed and list them in HANDOFF.

## Parts

### WEB1: the embedded server and its safety (new files `DesktopWebServer.kt`, `DesktopWebAuth.kt`, `DesktopWebRouter.kt`, `DesktopWebSettings.kt`, tests; hooks in `Main.kt`, `DesktopApp.kt` settings, tray menu)
1. `DesktopWebServer`: start/stop on a chosen port (default 8765; if taken, try the next 20), `HttpServer` with a bounded thread pool (2 to 4 daemon threads), graceful stop. Static files from the classpath folder `web/` (`desktopApp/src/main/resources/web/`), with correct content types, `Cache-Control` for hashed assets, ETag for the rest, and a small built-in fallback page when the folder is empty ("Muses Web is running").
2. `DesktopWebAuth`: random 128-bit token generated per launch, delivered as an `HttpOnly; SameSite=Strict` cookie when the page loads from the server (only from loopback unless LAN is enabled); LAN mode needs a 6 digit pairing code shown in Settings and entered once in the browser; `Host` allowlist (`localhost`, `127.0.0.1`, the LAN IP when enabled); pure functions for all checks, tested.
3. `DesktopWebRouter`: a tiny pure router (method, path template with `{param}`, handler) with JSON helpers over kotlinx.serialization, error envelope `{error, code}`, request body size caps, and `/api/ping` and `/api/events` (SSE with a keep-alive comment every 20 s and clean disconnect handling). All handlers are `suspend` and run on a dedicated `CoroutineScope` that is cancelled on stop.
4. Settings (new "Web" group under Experimental; look at `DesktopSettingsCategory` from S1 and the voice/earbuds groups): master switch "Muses Web (experimental)", port, "Allow other devices on my network" (off), the pairing code, "Open in browser" button (`Desktop.browse`), "Start without the desktop window (background mode)".
5. **Headless/background mode**: a command-line flag `--web` (and the setting above) that starts the server and the tray icon WITHOUT creating the Compose window or the animated backdrops; the tray menu gets "Open Muses Web", "Show the desktop window" (creates it on demand, then the app behaves as today) and "Quit". Look at `Main.kt`'s tray/window lifecycle first (`Window(visible=false)` is used for the tray today) and reuse it; the window must not be created or composed in background mode. Playback state that the server needs must not depend on a composed window (note anything that does in HANDOFF).
6. Add `jdk.httpserver` to the packaged `modules(...)` list; no other build change.
7. Tests: router matching and params, token/cookie/Host checks, Range header parsing helper (here, reused in WEB2), SSE formatting, body-size cap.
Acceptance: with the switch off nothing listens; on, `GET /` serves a page and `/api/ping` answers only with the cookie; a request with a foreign `Host` or no cookie gets 403.

### WEB2: the API adapters (new file `DesktopWebApi.kt` plus small helpers, tests; hooks where existing functions are reached)
Wire each endpoint of the contract to the EXISTING Kotlin code (find it with grep; do not duplicate logic): home feed and shelves (what `HomeScreen` is fed with), search and suggestions, library/playlists (the account's own and saved), playlist contents, track details, lyrics, like, add-to-playlist (use the same call the voice adapter and the player button use), artwork proxy, and the **palette** endpoint (read the cover through the existing artwork cache and use `extractAlbumPalette` to return the three display colours as hex, so the browser can tint a static gradient without doing any image work).
**Stream proxy** `/api/stream/{videoId}`: resolve with the existing `StreamResolver`/`PlayerClient`; fetch the upstream URL with the existing HTTP client honouring the browser's `Range` header (reuse the logic in `DesktopRangeStream.kt` if it fits); respond `206/200` with `Content-Range`, `Content-Length`, `Accept-Ranges: bytes`, and a content type the browser plays (prefer `audio/mp4` AAC; if only webm/opus is available that plays in Chromium and Firefox but not old Safari: return the type honestly); stream with a small bounded buffer (never hold a whole file in memory); handle client aborts without leaking the upstream connection; refresh the resolved URL once when upstream answers 403/410; **allowlist** the upstream host. Cache resolved URLs in memory for their validity window (look at how the desktop player caches).
Concurrency: at most 3 simultaneous streams and 8 art fetches; return 429 beyond that.
`/api/voice`: accept the audio body (16 kHz mono WAV, or decode webm/opus through the existing ffmpeg/sidecar helpers only if the repo already ships them; else require WAV and let the web UI produce WAV), run the existing recogniser and command parser, return the result in the contract shape WITHOUT executing playback commands on the PC (in web mode the command is returned to the page, which plays in the browser): add a function in the voice code that parses and resolves to an `Item`/action without side effects, reusing the library index and matcher. Never store audio or text.
Tests: pure helpers (Range handling, host allowlist, JSON shapes, palette to hex).
Acceptance: every endpoint in the contract answers with the documented shape; no endpoint can fetch an arbitrary URL.

### WEB3: the web UI, light by design (new folder `desktopApp/src/main/resources/web/` with `index.html`, `app.css`, `app.js` and ES modules under `js/`, `manifest.webmanifest`, `sw.js`, icons from the existing Logo; no build step)
1. Shell: hash router (`#/home`, `#/search?q=`, `#/library`, `#/playlist/<id>`, `#/now`), top bar (logo, search box with suggestions, account avatar), bottom mini-player bar, responsive layout: phone (single column, bottom tabs), tablet, desktop (left rail optional). Semantic HTML, keyboard accessible, 44 px touch targets.
2. **Performance and battery rules (these are the point of the project):** no JS animation libraries, no canvas, no blur animations; CSS transitions only on `transform`/`opacity` and only when `prefers-reduced-motion` is not set; one static glass style (`backdrop-filter` on the top bar and mini player only, with a solid fallback when unsupported or when "Data/Battery saver" is on); lists use `content-visibility: auto` and `loading="lazy" decoding="async"` images with explicit sizes; horizontal shelves use CSS scroll-snap; no polling (use SSE and the audio element's own events); update the progress bar at most 4 times per second and not at all when the tab is hidden (`visibilitychange`); drop the page's work to near zero when hidden.
3. **Themes:** Light, Dark, AMOLED black, and "Album tint" which is a STATIC two or three colour CSS gradient from the `/api/track` palette (changed with a short opacity cross-fade, no moving orbs); a battery-saver toggle that turns off blur and transitions; the choice is saved in `localStorage`.
4. Pages: Home (shelves like the desktop home: Recents, Song mixes, Listen again, From your library, Albums for you), Search (typeahead, sections), Library (playlists), Playlist (tracks, play, shuffle, add to playlist, like), Now Playing (large art, title, scrubber, transport, lyrics tab with synced highlight using `requestAnimationFrame` ONLY while the lyrics tab is visible and playing, queue tab).
5. PWA: manifest and a service worker that caches only the app shell (never audio or API), with a version string and an update prompt.
6. Everything talks only to the contract above, through one small `api.js` module (fetch with the cookie, error envelope handling, retry once, abort controllers on navigation).
Acceptance: the page loads without errors from the server, works with scripts split in ES modules, passes a manual checklist in `docs/WEB_UI_CHECKLIST.md` (written by you: layout sizes, themes, reduced motion, offline shell, keyboard use); total first-load transfer under about 150 KB excluding images.

### WEB4: the player, click-to-speak and polish (new JS modules `player.js`, `voice.js`, `settings.js`, `mediasession.js`, the Settings view, README section, tests are manual checklists)
1. **Player (`player.js`)**: one `<audio>` element; queue model (play now, play next, add to queue, shuffle, repeat off/all/one), next/previous, seek, volume, mute; preload the next track's stream by resolving `/api/track/<next>` early and setting `preload="auto"` only on a second hidden `Audio` object when the current one has 20 s left (one extra connection at most); resume the last queue position from `localStorage` (ids and position only, no names or search text); error handling with one automatic retry per track and a visible message, then skip; end-of-queue behaviour.
2. **Media Session API** (`mediasession.js`): metadata (title, artist, artwork), play/pause/next/previous/seek actions and position state, so the OS media keys, lock screen and Bluetooth buttons work with the tab in the background.
3. **Click-to-speak (`voice.js`)**: a microphone button in the top bar (and a large one on Now Playing). Click once to start, it records until silence (simple energy end-pointer, 600 ms) or 8 s, or click again to stop; a "hold to talk" option for pointer devices in Settings. Capture with `getUserMedia` and an `AudioWorklet` (or `MediaRecorder` if worklets are unavailable) producing 16 kHz mono 16-bit WAV in memory, with **300 ms of leading and trailing near-silence padding added and the microphone started BEFORE the "listening" state is shown** (show "Listening" only after the first audio frame arrives, and make any sound cue play after that and be excluded from the recording), so the first words are not lost. POST to `/api/voice`, show the recognised words briefly with the result, offer up to 3 choices when ambiguous, play the chosen item in the browser, then discard everything. Works on `localhost` or HTTPS only; show a clear message otherwise.
4. Settings view: theme, battery saver, stream quality hint (prefer AAC/low bitrate), "Open desktop window", sign-in status, voice options, "About and licences".
5. Docs: README section "Muses Web" (what it is, how to start it, the limits listed under "Honest limits"), `docs/WEB_SERVER.md` (API contract, security model, how to run headless), battery notes (what is turned off and why).
6. Manual test checklist in `docs/WEB_UI_CHECKLIST.md` extended: play, seek, next, background tab with media keys, voice on localhost, battery saver, reduced motion, offline shell.
Acceptance: a song plays in a browser tab and keeps playing with the tab hidden; media keys work; click-to-speak plays a requested song; the page stays idle (no timers firing) when nothing is playing.
