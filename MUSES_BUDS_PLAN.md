## Product
- Experimental, opt-in (Settings > Experimental, "Earbuds"). Off by default; nothing is scanned or opened until it is on.
- When a compatible pair of earbuds is connected to the laptop, a small **earbuds chip** appears in the floating pill (Classic and Liquid pills): battery for left, right and case (with a charging mark), and a tap opens a small popup with the noise modes (Off, Noise cancelling, Transparency, Adaptive; only the modes the buds report) and a Low latency switch. The chip disappears when they disconnect. The owner pairs the buds in Windows Bluetooth settings as usual; Muses never pairs.
- **What "compatible" means:** the vendor-app family that QuickBuds supports: OnePlus (Buds, Nord Buds, Bullets Wireless), OPPO (Enco), realme (Buds, Buds Air, Buds Wireless, TechLife), DIZO. These earbuds speak one proprietary protocol over classic Bluetooth (RFCOMM). Earbuds from other brands (Sony, Samsung, Apple, boAt, Nothing...) use different protocols and are NOT supported by this feature; for them nothing appears (an optional battery-only fallback is in B3).
- Features come from what the earbuds REPORT, not from a model table: the broadcast-codes reply and the feature-switch status reply decide which controls are shown.

## Protocol facts (from QuickBuds' PROTOCOL.md; verified on OnePlus Buds 4 there, other models may differ; use only what is listed)
- Transport: classic Bluetooth RFCOMM (SPP), NOT BLE. Service UUIDs tried in this order: `0000079A-D102-11E1-9B23-00025B00A5A5` (the one that works on Buds 4), then `00001107-D102-11E1-9B23-00025B00A5A5`. One long-lived socket; the buds push events at any time. The first UUID failing on some models is normal.
- Frame: `AA <TotalLen> 00 00 <Cmd LE 2B> <Seq 1B> <PayLen LE 2B> <Payload>`. `TotalLen = bytes after the header and the length field` = `7 + PayLen`... (worked examples: handshake `AA 07 00 00 00 01 01 00 00`; set ANC off `AA 0A 00 00 04 04 06 03 00 01 01 01`; ANC push `AA 0C 00 00 04 02 FF 05 00 03 01 01 08 00`). Seq is `0x01..0xFE` for our requests; **`0xFF` = a push from the buds**. **TotalLen is LEB128** (value < 128 is one byte; for >= 128 subtract 1 then 7-bit groups; decode adds 1 back); our own frames are small, but the parser must handle the long form. **The payload always starts at byte index 9**; its size is bytes 7-8. Responses are `cmd | 0x8000`.
- Init sequence, 200 ms apart, 300 ms before the first: `0x0100` handshake; `0x0103` product id; `0x0200` broadcast codes (reply `0x8200`: `[count][codes]`, tells what the firmware supports); `0x0205` **register for pushes, payload `[count][eventId...]`, count FIRST** (`03 01 02 03` = battery + wearing + ANC); `0x010D` feature status (request `[count][featureIds...]`, reply `[status=00][count][featureId][value]...`); `0x010C` ANC (`01 01` = current mode); `0x0106` battery; `0x0109` wearing. Then poll status every 60 s; do not poll wearing (it is pushed).
- Battery: reply `0x8106` and push `0x0204` subType `01`: triples `[index][raw]`, index `01` left, `02` right, `03` case; level = `raw & 0x7F`; charging = `(raw & 0x80) != 0`. The case battery is only sent while the lid is open.
- Wearing: reply `0x8109` / push subType `02`: `[count][component,status]*`; component 1 left, 2 right, 3 case; status 3 or 7 in ear, 4 in case, 1 or 5 idle, 0 disconnected. Some replies have an extra leading status byte: try offset 0 and offset 1 and keep the plausible one. Closing the case lid sends an all-zero wear push, then the socket drops: treat as a disconnect, retry when the link returns.
- Noise control, **SET and NOTIFY use DIFFERENT encodings**. Set: command `0x0404`, payload `01 01 <bitfield>`: Off `01 01 01`, On `01 01 02`, Transparency `01 01 04`, Deep `01 01 10`, Medium `01 01 20`, Light `01 01 40`, Smart `01 01 80`, **Adaptive `01 01 00 08` (four bytes; bit 11, not bit 8)**. The reply is `0x8404` with payload `00` for success. Notify: push `0x0204` subType `03`, payload `03 01 01 LO HI`, and the `0x810C` reply to `01 01` carries the same last two bytes: `08 00` Off, `02 00` ANC (generic), `80 00` Smart, `40 00` Light, `20 00` Medium, `10 00` Deep, `00 01` Transparency, `00 02` Transparency with voice enhance, `00 08` Adaptive. The notify value is a bitmask of the actual mode (the ANC-on stop echoes the last LEVEL), so decode with a mask test, never an enum. **A `0x0204` subType `03` whose bytes 1 and 2 are not `01 01` is NOT a mode change** (it is the echo of a gesture-cycle write): ignore it.
- Feature switch: `0x0403` payload `[featureId][01|00]`, ack `0x8403 00`. Feature ids: `0x04` wear detection/auto pause, `0x06` game mode (low latency, legacy), `0x28` game mode (newer devices), `0x09` vocal enhance, `0x11` dual device, `0x18` hi-res (LHDC; changing it DROPS the link for about 4 s), `0x1B` spatial sound. Use the id the earbuds list in their `0x810D` reply (`0x28` if present, else `0x06`).
- Silence is not absence: an unsubscribed event looks exactly like a feature the firmware does not report. Writes with a wrong command number fail in total silence: always read the state back after a write and show the real state.
- Windows allows one RFCOMM client per service at a time (UNVERIFIED): if QuickBuds or HeyMelody is connected, our connect will fail; show "Another app is controlling these earbuds. Close it and try again" for a connect failure on an otherwise healthy link.

## Parts

### B1: protocol core, pure Kotlin (new files `DesktopBudsProtocol.kt`, `DesktopBudsSession.kt`, `DesktopBudsNames.kt`, tests)
1. Frame builder/parser: LEB128 `TotalLen` encode/decode (tested with short and long frames), a streaming parser that accepts arbitrary byte chunks (frames split or joined), resynchronises on `0xAA`, rejects impossible lengths, and never throws. Payload offset 9. Command constants as named values.
2. Parsers: battery, wearing (offset 0/1 tolerance), ANC notify mask, feature-status reply, broadcast-codes reply, product id (keep the raw bytes as hex; a model name is not needed). Builders: handshake, product id query, broadcast query, register pushes, status query, ANC query, battery query, wearing query, set ANC (including the four-byte Adaptive), feature switch.
3. `BudsSession`: runs the init sequence with the delays above over a `BudsTransport` (virtual-time friendly: take a delay function/clock), keeps `BudsState`, applies pushes (seq `0xFF`) and replies, polls every 60 s, `setNoiseMode` sends the set command, waits for the ack and the read-back, and returns true only if the read-back matches (bounded wait about 2 s); `setLowLatency` the same with the right feature id. A closed transport (`read` returns -1) sets `connected = false` and stops.
4. `DesktopBudsNames.isLikelyCompatible(name)`: case-insensitive patterns for OnePlus Buds / Nord Buds / Bullets Wireless, OPPO Enco, realme Buds / Buds Air / Buds Wireless / TechLife Buds, DIZO Wireless / GoPods. A pure, data-driven list.
5. Tests: the worked-example frames from "Protocol facts" byte for byte; split/joined chunks; LEB128 round trip; battery, wearing and ANC decode tables including the "mask, not enum" rule and the "ignore subType 03 whose bytes 1-2 are not 01 01" rule; a fake transport driving a full init and a noise-mode change; a lid-close all-zero wear push; name matching positives and negatives.
Acceptance: all pure; no Windows or Compose import in these files; every frame constant traces to the facts above.

### B2: Windows Bluetooth transport and device discovery (new file `DesktopBudsWindows.kt`, tests for the pure parts)
1. Own minimal JNA interfaces: `ws2_32` (`WSAStartup`, `WSACleanup`, `socket`, `connect`, `send`, `recv`, `closesocket`, `setsockopt` for receive timeout, `WSAGetLastError`) and `bthprops.cpl` (`BluetoothFindFirstDevice`, `BluetoothFindNextDevice`, `BluetoothFindDeviceClose`, `BluetoothGetDeviceInfo` or the equivalent with `BLUETOOTH_DEVICE_SEARCH_PARAMS` / `BLUETOOTH_DEVICE_INFO`). Define the structures as JNA `Structure` subclasses with the exact Win32 field order and sizes (SOCKADDR_BTH: family `USHORT` = `AF_BTH` 32, `btAddr` `ULONGLONG`, `serviceClassId` `GUID` 16 bytes, `port` `ULONG`; BLUETOOTH_DEVICE_INFO: size, address, class of device, `fConnected`, `fRemembered`, `fAuthenticated`, last seen/used SYSTEMTIMEs, name `WCHAR[248]`). Check each constant and layout against the Win32 documentation you remember; note anything unverified in HANDOFF.
2. `DesktopBudsDevices.connectedCompatible()`: enumerate remembered/paired devices without issuing a new inquiry (`fIssueInquiry = false`), keep those with `fConnected` true and `DesktopBudsNames.isLikelyCompatible(name)`. Cheap, off the UI thread, no results cached beyond the call. Never log names or addresses (short hash only).
3. `WindowsRfcommTransport.open(device)`: for each UUID in order (`0000079A-...`, then `00001107-...`) create an `AF_BTH`/`SOCK_STREAM`/`BTHPROTO_RFCOMM` socket and `connect` with `serviceClassId` = the UUID and `port = 0` so Windows resolves the channel by SDP; bounded connect time (about 6 s) by running connect on a worker and closing the socket on timeout; first success wins. `read` uses a receive timeout loop so a cancelled coroutine can stop it; `close` closes the socket and calls `WSACleanup` when the last transport closes. Map `WSAGetLastError` values to codes (`ALREADY_IN_USE`, `NOT_CONNECTED`, `TIMEOUT`, `UNKNOWN`) for B3's messages.
4. Everything is a no-op returning empty / failure on non-Windows; JNA is loaded lazily the first time a Windows method is called (same guard pattern as other Windows files).

Acceptance: no Windows class is touched at class-load time on Linux; every native call is wrapped so a failure returns `Result.failure`, never throws to the UI.
